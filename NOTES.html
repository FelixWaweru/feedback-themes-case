How model choice shows up: Both measured runs clear Gates 1–2. GLM wins on cost (~6× cheaper than Kimi; 94% under the $6 floor). Kimi wins on wall clock (~2.4× faster end-to-end), reliability (0 vs 4 extract failures), and a denser specific tier (47 vs 39). Frontier benchmarks (list-price estimates on the same max token envelope): GPT-5.5 ~$6.00 sits at the $6 gate; Claude Fable 5 ~$11.21 overshoots it.
Presentation takeaway: Same code path, different models → different taxonomies, costs, and failure modes. Ship Kimi when extract quality/reliability matters; switch to GLM when you need the cheapest gate-clearing run and can tolerate a few JSON retries. GPT-5.5 and Fable show why a frontier flagship is unnecessary for this brief once Kimi/GLM already clear both gates.

Theme set

Themes come from batched discovery over all 223 reviews (9×25), then one synthesis call into a nested registry (data/themes.json / data/theme_set.md). Names are polarity-neutral subjects so praise and complaints map to the same path. Each model invents its own labels from the same reviews:

  • Kimi (shipped): 7 strategic / 20 midlevel / 47 specific: denser leaves; top specifics skew to rate competitiveness, staff professionalism, reply speed.
  • GLM: 8 strategic / 21 midlevel / 39 specific: slightly broader strategic cut, fewer specifics; top specifics skew to rate/fee trade-offs, loan limits, support reply speed.

Hard calls (visible on both): ultra-short praise often stays empty; authenticity complaints lack a dedicated leaf; multi-topic reviews still under-assign occasionally.

Decisions the brief left open

  • Constrained taxonomy + path enum: free-form names broke TREE As suggested, assignment schema is an enum of full A > B > C labels with post-parse repair for scrambled triples.
  • Discover then extract: same model for both stages in each experiment so taxonomy and assignment stay aligned.
  • Rich categorisation.json + derived out/flat.json: meaning lives in the nested file; flat is the checker projection.
  • Ship Kimi over GLM: pay ~$2 more for zero parse failures, faster wall clock, and denser specifics; keep GLM as the budget path.
  • Official openrouter SDK; cost is summed usage.cost, never recomputed from list prices.

Architecture

Two stages, same model for both: first invent a reusable theme tree from the reviews, then label each review against that tree. Discovery works in batches of ~25 reviews in parallel; extraction fans out one review per worker (8 at a time). Results are checkpointed so a mid-run crash does not lose finished work.

What I would do with another week

  • Retry/JSON-repair loop for GLM-class structured-output failures (the 4 non-JSON reviews).
  • Second pass only on empty reviews that contain operational nouns (fast, fee, portal, advisor).
  • Add a recurring “review authenticity / trust in feedback” leaf if discovery keeps surfacing it.
  • Prompt-cache the taxonomy block to cut Kimi input cost.
  • Small hand-labelled calibration set to tune empty-vs-assign policy for 1–2 sentence reviews.
  • Re-time on a dedicated server. These runs were on an active workstation with 8 GB RAM (Chrome and other apps open during the test), so wall clock includes local contention. A quieter host with more RAM/CPU: and larger discovery batch sizes / higher worker counts: could cut elapsed time further without changing models.
